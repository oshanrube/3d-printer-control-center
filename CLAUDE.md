# 3D Printer Control Center: project context

A self-hosted control center for a fleet of Creality/Klipper printers, running on an Orange Pi at home. A **Node/TypeScript backend** reads every printer (Moonraker, plus Creality's own firmware feed), runs a **failure-detection engine** (auto-pause, push alerts, dataset logging for future AI training), and relays cameras. A **Preact PWA** frontend shows the live fleet.

Repo: `oshanrube/3d-printer-control-center`, default branch **`master`**. The old static dashboard (HTML + Caddy proxy) is kept in `legacy/` for reference only.

### Internet path and remote access
```
Internet ── SLT fibre (CGNAT) ── Huawei HG8245H5 ONT (192.168.10.1) ── Tenda router (10.0.68.1) ── Pi (10.0.68.53)
```

- The ISP (SLT) uses **CGNAT**: a traceroute's hop after the Huawei is `100.94.0.1`. The shared public IPv4 is not ours, so **port forwarding can't work**. The Huawei's SLT firmware doesn't display its WAN IP anywhere. The Huawei has IPv6 (DHCPv6-PD), but the Tenda doesn't pass it through.

Only the owner's devices can reach it, so the app's missing login isn't exposed. Web Push works on this origin. Notifications are delivered by Google, so they arrive even when the phone's Tailscale is off; opening the dashboard needs Tailscale on.

## Architecture

```
backend/src/
  index.ts         startup: seed DB, init push, start relay, fleet, engine, server
  config.ts        env-driven settings (see below)
  types.ts         Printer, LiveState, PrinterEvent, EventType
  db.ts            better-sqlite3: printers, events, push_subscriptions, kv (VAPID), prints, telemetry
  moonraker.ts     resilient Moonraker JSON-RPC WebSocket client (subscribe, pause/resume/cancel, gcode)
  creality.ts      read-only client for the firmware feed ws://<printer>:9999 (faults, pre-print state)
  fleet.ts         one Moonraker + one Creality client per printer -> normalized LiveState
  engine.ts        detection rules, events, push, dataset capture
  ai-analyzer.ts   AI failure detection: Obico detector on bc250 (+ optional vision-LLM second opinion)
  errors.ts        readable Klipper/Creality error text + hints
  camera.ts        snapshot API: WebRTC relay frame or MJPEG fetch; captureForDataset()
  webrtc-relay.ts  headless-Chromium WebRTC -> JPEG relay (see Cameras)
  push.ts          Web Push (VAPID keys persisted in kv)
  scan.ts          LAN scan for Moonraker (:7125)
  server.ts        Fastify REST + /ws live stream + static frontend
frontend/src/      Preact + Vite PWA: store.ts (WS-backed), App.tsx (cards, cameras, events, modals), push.ts, sw.js
```

REST: `GET/POST/PATCH/DELETE /api/printers`, `POST /api/printers/:id/{pause|resume|cancel}`, `GET /api/events`, `GET /api/prints`, `GET /api/camera/:id/snapshot`, `GET /api/scan`, `/api/push/{vapid,subscribe,unsubscribe,test}`. WS `/ws` sends a snapshot, then streams state and events.

Stack: Fastify 4, @fastify/websocket 8, better-sqlite3 11, web-push, ws, puppeteer-core 23, Node 20 (bookworm-slim, with Debian Chromium in the image). Multi-stage `Dockerfile`.

## Notifications
- Web Push via `push.ts`. **Warnings and critical alerts use `urgency: high`** (TTL 6 h), so Android delivers them immediately even when the phone is idle (Doze). With the default "normal", alerts were held back. On 2026-11-09 a Nami jam warning and spaghetti alerts were raised but you weren't notified in time. Tags are per printer *and* event type, so one alert can't silently replace another. Each pushed event stores `push_result` (e.g. "sent to 2/2"), shown in the events feed.

## Failure labels
- After a print ends **cancelled/error**, the printer card asks "Why did the last print stop?" (with its last frame): spaghetti, jam, layer_shift, warping, adhesion, wrong_file, not_failed, other (+note). A 🏷️ counter in the top bar opens all unlabelled stopped prints (last 7 days), and an "All recent" tab for marking a *completed* print as bad. Stored as `prints.failure_reason` / `failure_note` / `labelled_at`. API: `GET /api/prints/unlabelled`, `GET /api/prints/finished`, `POST /api/prints/:id/label`, `GET /api/prints/:id/last-frame`.

## Detection engine (`engine.ts`)
- Print started / finished / cancelled, tracked with an `inPrint` flag: only transitions the engine actually saw count, so backend restarts and reconnects can't replay a finished print (this used to happen on every restart) or re-announce a running one. A dropped connection doesn't end dataset capture.
- Klipper error (critical), once per distinct error (not on every reconnect; remembered in `kv klippererr:<id>` across restarts). **Klipper shutdowns** only show in the `webhooks` object (`state: shutdown`, `state_message`), which is now subscribed: live state becomes `error`, and the alert names the earlier cause from the `!!` G-code error lines (e.g. K2 2026-11-11: `key60` "Internal error on command:G28", caused by `key789` closed-loop Z motor position tracking error on z1/z2 during pre-print homing, after a `key840` CFS box switch error). Creality's JSON errors (sometimes malformed) are made readable in `errors.ts`, with hints for confirmed codes (`key586` = move out of range, usually a file sliced for another printer model).
- Printer offline (warning during a print).
- Filament runout while printing -> critical + **auto-pause**. Only **enabled** sensors count: the K2's `filament_switch_sensor` is disabled (it feeds from its rack/CFS) and always reads `filament_detected: false`, which until 2026-11-10 caused false runout alerts and **auto-paused K2 prints** whenever the engine's sensor memory reset (a restart or reconnect). Its pause macro then parked at Y≈362 (past the ~350 mm bed), and the firmware briefly reported 2586.
- Stall: no progress for `STALL_MINUTES` while printing.
- **"Preparing" on the dashboard:** Creality runs the pre-print phase (heating, levelling, bed camera check) before handing the job to Klipper, so Klipper still reports the previous print's complete/cancelled state and filename. When the Creality feed says busy (`state 1`, no fault) and Klipper isn't printing/paused, live state sets `preparing: true` and `vendorFile` (the feed's `printFileName`). The card shows "Preparing" + the new file + "warming up / calibrating"; the overview counts it as printing. Display only: engine rules keep using Klipper's state.
- **Firmware fault memory survives restarts** (`kv fault:<printerId>` = alerted code), so an active fault isn't re-sent after a restart. Firmware codes **2xxx mirror Klipper keyXXX** (2586 = key586 "Move out of range") and are described with Klipper's text + coordinates (`errors.ts describeMirroredKlipperFault`).
- **Creality fault** (from `:9999`) -> critical push explaining the code and whether heaters are still on; `fault_cleared` when it goes away. The firmware also mirrors Klipper errors as its own codes (Klipper `key586` -> Creality `2586`); after a 5 s settle, a fault is skipped if Klipper is in error, since the Klipper alert already covers it.
- **Power-loss watch (since 2026-11-17):** after a power cut on 2026-11-16 (printers rebooted ~13:33, the Pi stayed up), the screen's power-loss "resume" was pressed too late and a batch was ruined. Now: a printer that went offline mid-print and comes back idle with Moonraker uptime < 15 min gets `M140 S<the print's bed temp>` at once (parts stay stuck; nozzle left to the firmware's resume), a critical push "⚡ lost power mid-print: press Resume on its screen", reminders every 2 min until it prints again (max 1 h), and the idle-heater watchdog skips it meanwhile. Store jobs aren't failed by the reboot (idle after `offline` is not a failure; idle for 60 min is). **Remote resume not done yet:** firmware web param `offContinue` (`web control off continue`, Sanji `master-server` strings; screen path = `dis set print control = 4` -> `control start power loss`) is the likely trigger, and `powerLoss` in the :9999 feed may flag a pending recovery, but neither is verified: sending it with a stale power-loss record could restart an old print mid-file, so test only with the owner on an idle printer with an empty bed.
- **Idle-heater watchdog:** heaters on (target > 0) with nothing printing -> alert at 15 min, `TURN_OFF_HEATERS` at 45 min, critical alert if still on 5 min later. Paused prints get the alert only. The firmware's pre-print phase (`vendorBusy`) is exempt for up to 60 min.
- **Idle light/fans off:** the light (`output_pin LED`) and switchable fans (`output_pin fan0` part cooling, `fan1` chamber/exhaust, `fan2` side/auxiliary; **`fan1` shares its pin with the automatic `temperature_fan chamber_fan`**, so they're the same physical fan) are switched off once each has been on for `IDLE_OFF_MIN` (10) while nothing is printing (not printing/paused, not in the firmware's pre-print phase). Timing is per device, so a light turned on later gets its full time. The **light goes through Creality's :9999 service** (`{"method":"set","params":{"lightSw":0|1}}`, as the Creality app does), because switching it with Klipper's `SET_PIN` works but leaves the **touch screen showing the old state** (Creality's `lightSw` doesn't follow Klipper). It falls back to `SET_PIN PIN=LED VALUE=x` if the feed is down. Fans use Creality's `M107 P<n>` macro, which also clears the hidden fan-enable pin (`fan0_en` on K2, `my_fan_output_pins` on K1C); the screen tracks fans correctly. **Light on at print start:** when a print starts or the firmware starts preparing one, the light is switched on if it's off (the AI detector and Creality's pre-print bed check need it). This happens once per print, so switching it off by hand mid-print is respected (`LIGHT_ON_PRINT`, default 1). Never touches `heater_fan hotend_fan`, `temperature_fan chamber_fan`, or the K2's `power`/`ptc_power`. Logged as an `idle_off` event (no push).
- **Chamber + fans on the dashboard:** `temperature_sensor chamber_temp` is the reliable chamber reading (on the K1C the automatic `chamber_fan` reads the same thermistor, `PC5`, with a different table and shows ~60°C when the chamber is ~43°C). The K2 adds `heater_generic chamber_heater` (target/power). The card shows Chamber and Light tiles plus a fan line: Part (fan0), Chamber (max of manual fan1 and automatic `temperature_fan`, marked "(auto)" when automatic), Side (fan2), Hotend (`heater_fan hotend_fan`), and Heater (K2 `heater_fan chamber_fan`, the chamber-heater circulation fan).
- **AI failure detection** (`ai-analyzer.ts`), see the bc250 section below.
- Dataset: during each print, a snapshot + telemetry row every 20 s into `data/snapshots/p<id>_<ts>/` and the `prints`/`telemetry` tables, labelled with the outcome. Intended for training a failure-detection model later.

## Auto-pause and reminders (`engine.autoPause`, since 2026-11-11)
- The AI detector (risk > 50%) and the jam detector call `engine.autoPause()`: it pauses, pushes (`auto_paused`, or a non-pushed `paused` row when the detector's own alert already said "Pausing"), and keeps a watch in `kv autopause:<id>` (survives restarts).
- While the print stays paused: a critical `pause_reminder` push every `PAUSE_REMIND_MIN` (5) min. If it never reaches "paused", the pause is re-sent once and the reminder says it hasn't paused yet. The watch ends when the print is resumed (printing again after the pause), cancelled, finished or errors.
- Klipper errors still use their own pause path (no reminders). **Filament runout reminders (since 2026-11-19):** a runout during a print starts a `kind: 'runout'` watch (same `kv autopause:<id>`): `🧵 <printer> is still out of filament (N min)` every `PAUSE_REMIND_MIN` until it prints again or is cancelled. We never send our own pause for it (the printer pauses itself); if it's still printing 60 s later the watch ends. No "auto-paused" flag on the card, and "Printing fine" never resumes a runout. Why: Sanji's runout at 23:28 on 11-18 sat paused 6 h 10 min (one push only); the cooled ABS parts shrank and the resumed layers left a seam/weak bond at ~165 mm (Klipper restored Z and the file position correctly: PAUSE lowers the bed 2 mm, or to Z 50 below 48 mm; RESUME moves back all but 2 mm and RESUME_BASE restores the rest).
- **"👍 Printing fine" (since 2026-11-13):** shown on the card while a detector is worried (reference "Differs", AI not "Looks OK", or auto-paused). `POST /api/printers/:id/looks-fine` -> `engine.confirmOk`: stores `kv printok:<id>` = the current print's key (`print-ok.ts`, dataset row id or file), turns off reference comparison and jam checks for the rest of that print, stops AI auto-pause and AI warnings (the failure-level alert still fires), and resumes the print if the engine auto-paused it. Why: a print in **black filament** differed from a white reference run (difference 1.04) and its heater power differed from its peers, so a healthy print was flagged and paused.

## Cameras
- **Tap a camera** on the dashboard for a full-screen live view (`CameraViewer`): pinch, scroll wheel, +/− buttons or double-tap to zoom (up to 6×), drag to pan.
- **WebRTC printers** (K2 is WebRTC-only; the three K1Cs run WebRTC too) use libpeer: `POST http://<ip>:8000/call/webrtc_local` with base64 JSON `{type:'offer',sdp}` and get back base64 `{type:'answer',sdp}`.
  - libpeer's answer includes a **payload type that isn't in the offer** (sometimes a garbage negative number). Browsers reject it, so the answer must be **munged to keep only PTs present in both offer and answer**.
  - WebRTC media is UDP/SRTP: it can't be HTTP-proxied.
  - **Only Chromium can decode it.** Dead ends: `aiortc` can't complete DTLS with libpeer; `@roamhq/wrtc` has no H264 decoder.
  - The relay drives one headless-Chromium page per printer, on demand. Live viewing holds a page warm (`touch`); dataset capture uses grab-and-release; idle pages are torn down.
  - **Keyframes-only decode (default):** printers send a keyframe every ~1.0 s (K2) / ~0.67 s (K1C). An encoded-insertable-streams transform drops delta frames before the decoder: full resolution at ~1–1.5 fps for ~0.3 core per camera, versus 1+ core for full decode. All 4 WebRTC cameras live ≈ 120% CPU total.
  - **WebCodecs decode (2026-11-17, the real fix):** all WebRTC cameras stopped showing frames although ICE/DTLS connected and video arrived (Chromium log: "No decodable frame ... requesting keyframe", "PacketBuffer is already at max size"). The RTP headers (cleartext in SRTP, read with a raw socket) showed well-formed frames (marker bits, one timestamp per frame) but **timestamps running ~20x too fast** (78.7 s of video time in 4 s), so Chromium's jitter buffer never rendered. The Creality app still worked; restarting `webrtc_local` (`/etc/init.d/S97webrtc restart`) and rebooting Sanji didn't help. The relay now takes the assembled keyframes from the encoded-insertable-streams reader and decodes them with **WebCodecs `VideoDecoder`** (codec string from the SPS, e.g. `avc1.4d001f`), drawing each to the canvas -> JPEG, bypassing the player and its timing. WebCodecs needs a secure context, so relay pages first load `http://127.0.0.1:<port>/relay-blank`. Falls back to the `<video>` path if `VideoDecoder` is missing. Verified: 4/4 cameras 200 continuously.
  - **Reconnect backoff (2026-11-17):** all four WebRTC cameras got stuck in a loop: no frame within 20 s -> page rebuilt -> immediate reconnect while the printer was still sending to the old session (libpeer drops it ~5 s after ICE disconnect, `Disconnect with browser... Stop streaming` in `webrtc_local.log`) -> the new session got packets but no frames -> rebuilt again. Probably started by today's many app restarts. Now a failed page waits 10 s before reconnecting, doubling up to 2 min on repeated failures; a frame resets it. Diagnosis that showed it: in-container Chromium test call (ICE/DTLS connected, RTP bytes arriving, `framesReceived` 0) vs a later clean call (keyframe every ~0.7 s, 0 loss).
  - **Restart diagnostics (2026-11-18):** each `restarting camera` log line ends with `diag=` (connection/ICE state, encoded frames and keyframes seen, frames decoded, last decoder error, inbound RTP bytes/packets/frames). `rtp:null` with `conn: connected` = the printer isn't sending video (K2 2026-11-18, mid-print, possibly another viewer holding its camera). That morning Sanji/Usopp/Nami were in the restart loop again; an app restart cleared it.
  - **Self-healing:** a page whose connection fails/closes, or that produces no frame within 20 s or stops producing frames for 15 s, is rebuilt on the next request. (Before this, a page whose connection dropped stayed open forever while the dashboard kept polling, and the camera showed 502 until a restart.)
  - Capture must be **timer-driven**: `requestVideoFrameCallback` doesn't fire in background tabs (every relay page but one). Background throttling is disabled via Chromium flags.
  - **No hardware decode:** the RK3566 VPU is only exposed through Rockchip's vendor MPP (`/dev/mpp_service`), which Chromium can't use (needs VAAPI or upstream V4L2). It would need a mainline kernel.
- **MJPEG on the 1.x K1Cs (since 2026-11-20, owner's go-ahead):** firmware 1.3.5.22 runs the same camera stack as 2.x: `cam_app` owns the camera and shares frames through memfd, and `webrtc_local` reads them. `mjpg_streamer` + `input_memfd.so` are installed, but Creality commented out the main camera's streamer lines in `/usr/bin/auto_uvc.sh` (start at lines 127-130, stop at 187). On Sanji, Usopp and Nami those 5 lines are uncommented (original backed up as `/usr/data/auto_uvc.sh.orig-20261120`; `/` is an overlay, so a firmware update/factory reset restores it), and the streamer was started by hand with the same command. **WebRTC keeps working alongside** (both read the memfd). MJPEG is full 1280x720 in ~0.1 s vs the relay's 800x450 at ~1 s; ~3% printer CPU at 1 frame/s. Dashboard `cameraType` for Sanji/Usopp/Nami = `mjpeg`. SSH to all three: `/root/.ssh/printers_ecdsa`. Not yet confirmed: that the edited script starts the streamer by itself after a reboot.
- **K2 cameras: no MJPEG (checked on .21, 2026-11-21).** The K2 runs OpenWrt 21.02 on armv7l (the K1Cs: Buildroot on MIPS). `cam_app -i /dev/v4l/by-id/main-video0 -t 0 -w 1920 -h 1080 -f 15 -c` owns the camera and `webrtc_local` gets frames over a local socket; `auto_uvc.sh` has no MJPEG lines and `mjpg_streamer`/plugins aren't installed. The K1C's `input_memfd.so` is Creality's closed MIPS plugin. **Reverse-engineered 2026-11-21 (`tools/k2cam/README.md`):** the camera outputs H.264 (1920x1080, keyframe 1/s); `cam_app` publishes it via Creality's `libdelivery` pub/sub on `/tmp/delivery_socket100`, topic 10000. A subscriber sends `[4][0x10000][myId]` then `[8][0x10001][myId][10000]` and gets `[len][10000][Annex-B H.264]` per frame. Tested with `tools/k2cam/k2probe.c` on Chopper mid-print (cam_app/webrtc_local unaffected); keyframes decode to 1080p JPEG on the Pi. **Built 2026-11-21:** the `k2cam` service on the printer (`tools/k2cam/k2cam.c`, procd `/etc/init.d/k2cam`, :8080 `/keyframe`, `/?action=snapshot`, `/status`) and camera type **`k2`** on the Pi (`backend/src/k2cam.ts`: live view decodes keyframes with one long-running ffmpeg per K2, ~0.10 core at 1 fps, stops when unwatched; dataset/AI use the printer's on-demand snapshot). Installed on Chopper (.21) only; Nico (.62) stays on the WebRTC relay until its long print is done (install steps in the README). The app image now includes ffmpeg. **Hardware H.264 decode on the K2 works** (Allwinner CedarC v1.3.0 via `dlopen`, `tools/k2cam/cedartest.c`): ~10 ms and 2.3 ms CPU per 1080p picture vs ~430 ms in software; details and pitfalls (register the codec with `CedarPluginVDInit`, no AUD) in the README. **k2cam on Chopper now does decode + scale + JPEG on the video engine** (`tools/k2cam/cedar_hw.c`, worker thread, ~20 ms and ~2.7% of a core at 1 JPEG/s, ffmpeg fallback), and the Pi takes those JPEGs for live view (`X-Encoder: hw`): Chopper's camera costs the Pi nothing. Hardware tests were done with Chopper idle (kernel driver); it has not yet run through a print. **K2 SSH:** OpenWrt Dropbear reads root's keys from `/etc/dropbear/authorized_keys` (not `/root/.ssh`) and rejects the ECDSA key: use `/root/.ssh/printers_ed25519` on the Pi. Installed on .21; .62 has keys in `/root/.ssh` only (added by mistake, unused).
- **MJPEG printers** (Luffy, Zoro): `mjpg_streamer` on `:8080` (`/usr/bin/mjpg_streamer -i input_memfd.so -t 0 -o output_http.so -w /usr/share/mjpg-streamer/www/ -p 8080`), and the backend polls snapshots. The K1Cs could in principle run this too, but that was dropped in favour of the universal WebRTC relay.
- Each printer allows a limited number of WebRTC viewers, so while the relay is watching, the Creality app may not get a stream (and vice versa).

## AI failure detection: Obico detector on the Pi's NPU (since 2026-11-10)
- **Runs on the Orange Pi's RK3566 NPU** as the `detector` compose service (profile `npu`; container `obico-detector`, image `obico-detector-npu:df8190e`, `detector/Dockerfile`), listening on **127.0.0.1:3333**. Start it with `docker compose --profile npu up -d detector`. App settings: `OBICO_URL=http://127.0.0.1:3333`, `OBICO_IMAGE_BASE=http://127.0.0.1:8081` (in `.env`). ## Reference-run comparison (`ref-compare.ts`)
Compares a print with a **successful run of the same file at the same step**. Klipper's progress is the G-code file position, so equal progress means the same layer. On the K1C/K2 the bed drops with Z under a fixed camera, so the part should look the same at the same step.
- **Method:** frames → 96×54 greyscale, ignore the top 42% (toolhead/gantry), z-score normalise. Current print = median of its last 3 frames; reference = median of the frames within ±0.25% progress. Score = mean absolute difference.
- **Validated on 2026-11-09:** same printer healthy vs healthy **0.02-0.10**; different K1C healthy vs healthy **0.15-0.26**; jammed vs healthy rises to **0.35-0.65** as material goes missing (Nami runs; Sanji's jam vs Luffy climbs 0.15→0.35 over 40→56%). Prototype: `data/research/refcompare.mjs`.
- **Limits:** 0.20 for a same-printer reference, 0.33 for another printer of the same model. Warn after 3 consecutive checks over the limit (every 2 min) with `reference_mismatch` (push warning, once per print).
- **References are successful runs only** (your call, 2026-11-09): prints that **completed** and weren't labelled bad afterwards, plus prints you labelled `not_failed` (up to where they stopped). Failed runs are never used, not even up to an estimated onset (an earlier version used Luffy's jammed run as "good until 55.5%"; that was only an estimate from heater power). Prints still running aren't used either. Same printer preferred, then same model. **Until a file has a successful run, nothing is compared.** Print fragments (`continued`, plus old `unknown` rows followed by the same file within 5 min) are grouped into one run.
- **UI:** the card shows "📐 Matches / Differs from a successful run …" with both progress values (now / reference) and a **Compare** button showing the reference frame for that step. A result is cleared the moment its print ends or another starts (an earlier version left a finished run's "Differs" and its mid-print reference frame showing next to a new print's first layers). Diagnostics: `GET /api/printers/:id/reference-debug` lists every candidate run with its healthy-until point. Results are stored in `ai_checks` (`source='reference'`, `score`).
- References improve on their own: once a run completes successfully, it becomes the exact same-printer reference for that file.

## Creality firmware facts
- `ws://<printer>:9999`: first message is a full snapshot, then deltas. Fields: `err {errcode,key,value}`, `state` (1 printing/preparing, 5 halted on error, 7 stopping, 4 stopped), `deviceState`, `model`, `printProgress`, targets. `creality.ts` never sends anything.

## Performance notes (Orange Pi)
- 2026-11-09: the Pi hit load ~14 on 4 cores. The main costs were `pmproxy` (PCP, ~0.9 core, **still to be disabled by the user**), 4 WebRTC relays (~0.25 core each), `tailscaled` (~0.25 core, encrypting camera images to the phone), and the backend.
- **Live updates are throttled** to 1/s per printer (`STATE_MIN_INTERVAL_MS`). Moonraker sends ~4/s of temperature noise; unthrottled, that was 23 messages/s and 16 KB/s per dashboard, and froze the page on slow CPUs (headless Chromium on the Pi never finished rendering). State, online, fault, error, file and AI-verdict changes bypass the throttle.
- **Camera polling** is once per second (the relay makes ~1 frame/s in keyframe mode) and pauses while the page is hidden.
- `motion_report` updates don't rebuild or broadcast live state (`fleet.ts`).
- **Restart race (fixed 2026-11-10):** the Creality feed can connect before Klipper's first status. Live state then fell back to "standby", and the real "printing" a moment later looked like a new print (false `print_started`, split dataset rows). Until `print_stats` arrives, the state now stays the `offline` placeholder, which the engine ignores. Seven split rows were relinked as `continued`.
- Headless Chromium in the app container has no emoji font, so emoji show as boxes in screenshots. That's cosmetic.

## Working model: Qwen does the work, Opus orchestrates and verifies (owner's rule, 2026-11-17)
**Split by difficulty (owner, 2026-11-17):** Qwen gets research, data gathering, log reading and small/mechanical edits from exact instructions; Opus writes logic-heavy code itself (on the store client, Qwen's two attempts didn't compile and repairing them cost more than writing it). Every session: plan the task, hand the Qwen-sized work to the worker with **`tools/qwen.sh`**, then **verify everything it claims** (diff, commit, files, outputs, live behaviour) before merging, building, deploying and pushing. Same model as the TDv3 projects (`/media/nvme/TDv3/.qwen/qwen.sh`).
- `tools/qwen.sh start <name> <read|edit|git> <prompt-file>`, `wait <name> [max-min]` (blocks, then prints the compact log), `status`, `log <name> [n]`, `stop`. Runs in the claude-agent container (headless Claude Code, `HOME=/root/.qwen-home`, key `/root/.config/qwen/api.key`, bc250 Qwen3.5-9B), cwd = repo; logs in `data/qwen-tasks/`. Prompts in `data/qwen-work/` (gitignored).
- Profiles: `read` (files, git history, GET via `tools/qwen-bin/http-get`), `edit` (+ Edit/Write, left uncommitted), `git` (+ add/commit on branch `qwen/<name>`, which the script cuts from master and refuses on a dirty tree). Denied: push, switch/merge/reset/checkout, rm/mv, curl/wget/ssh, docker, systemctl, python/node, env, `/root/**`, `.env`. **No curl** because prefix rules can be dodged (`curl -s -m5 -X POST` would pause a printer); `http-get` only ever does GET.
- After a `git` task: check `git show`, then `git switch master && git merge --ff-only qwen/<name>`, delete the branch, build/deploy with compose, verify live, push from the Pi host.
- Qwen: 64k context, one request at a time (shared with Happier), ~45-50 tok/s, ~1-2 min startup per task. Write prompts as explicit numbered steps with exact paths, URLs and expected output. It stops on any refusal (by design). There is no Node in the container: Opus type-checks via the Docker build.
- **It invents things:** on the 509 task it fabricated a log quote, cited the wrong source and ordered a fallback badly. Verify every quote, count and claim.

## Gotchas for agents
- The Pi's `/bin/sh` is **dash**: no bash-isms (`declare -A`, etc.) in host one-liners.
- Neither the Pi nor the old agent container has `sshpass`. For printer SSH, use `SSH_ASKPASS` + `SSH_ASKPASS_REQUIRE=force` + `setsid`.
- The old agent container had no `node`. Run Node scripts inside the app container: put the file in `data/`, then `docker exec 3d-printer-control-center node /data/<file>`.
- **Browser/API tests must only touch records the test created** (a throwaway part or item it sets up and removes). On 2026-11-17 a UI test clicked "the first checkbox" and "the first Edit recipe" on the live Inventory page and changed two of the owner's configured items (fixed by hand). The live store/inventory data is the owner's.
- **Before deploying, check no store job is uploading** (`GET /api/store/jobs`, status `loading`): a restart cuts the upload off (2026-11-17 Sanji). Startup marks such jobs cancelled so they're reloaded, but the printer waits until then.
- **Never start the app with `docker run`**: always `docker compose build control-center && docker compose up -d control-center`. A bare `docker run` has no data volume or `.env` (see the 2026-11-15 incident).
- Commit messages with apostrophes break `sh -c '...'` quoting: write the message to a file and use `git commit -F`.
- Auto-mode safety checks blocked: writes or service changes on printers over SSH, disabling logging/metrics services on the Pi, and reading printer init scripts. Ask the user, or have them add a permission rule; don't work around it.
- The printers are in production. Never interrupt an active print; check `print_stats.state` first.
